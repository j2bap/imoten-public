Delegation, lifecycle, isolation, history, and capability fallbacks follow `../references/codex-agent-runtime.md`.

### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-ID rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. The operator reviews and clicks, and no owner merges one. A request to state the plan is not a go. Execution starts only on the operator's explicit go. That go authorizes creating a goal with the full program objective and a thread heartbeat until the queue is done.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once through `../references/forge.md`. One isolated agent VM or remote task per PR owns build, the first push, a ready PR per `playbooks/opening-a-pr.md`, self-proof on the real artifact, skeptical Bugbot triage, `$deslop`, `$no-comments`, a rebase onto current trunk, babysit to green per `playbooks/babysit.md`, and the merge once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after `$deslop` and `$no-comments`, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head SHA before self-proof, so verification runs on the base the patch lands on. Report the SHA of every later push that changes the patch, and merge-ready with the head SHA once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the pre-review checks that the repository's AGENTS.md files and rules name for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier. A hook pass is not proof.

   Assume the VM dies. Before self-proof, every owner starts `decisions.tsv`, pushes its first branch snapshot, and opens the ready PR. Then it pushes after every verifiable unit with hooks on. A WIP commit is allowed. As soon as a delegate starts, the owner adds its ID, expected runtime, and state to a local `children.tsv`, so the root can probe it if the parent dies. The expected runtime is at least the longest past run of that kind. Force-push only your own branch, with `git push --force-with-lease` after a `git ls-remote` check, pinned to the SHA you last pushed or took over. On any push you did not make, stop and report to the root. Never force-push a shared branch.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own. Give each owner one branch and disjoint files. Serialize overlapping work. An owner may keep a short private base-branch stack for a dependent split.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through its control skill (such as `control-ui` or `control-cli`) or a named driver, and audit the diff. Run the audit as two or more review lanes with the full brief, each with one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. One lane runs the same load-bearing scenario on trunk. If trunk lacks the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for. A clean verdict follows the aggregate rule in `../references/verdicts.md`. It is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test across every site with the same defect. Where no test can show the defect, ask for a repro receipt. Add that defect to the next round's review brief. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head SHA, and waits for green CI. The patch-ID rule decides whether the round's verdict still holds on that head.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a `git merge-tree` conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. The owner squash-merges through the selected forge and returns. A fresh owner takes the next self-contained item. The operator's full-autonomy grant plus the root's clean verdict authorizes the merge. Operator-owned items stop at merge-ready.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval. The owner records it in the form that the forge's approval contract allows, with a pointer to your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, use the authorized thread heartbeat for audit ticks every hour until no delegated work is left, because long runs drift and agents stall silently. Never hold a shell open to sleep. Each tick re-reads this playbook from trunk and inspects the live goal. It fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, through supported live status and judges each by its side effects, because status text and summaries can hide a stuck child. The tick also reads every owner's `children.tsv` and the program's agent list, where the runtime exposes one. An agent is stuck when it errors, cannot start turns, or shows nothing new past its expected runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. Whether or not a stop works, the owner records each stuck delegate as stuck and replaces it if its work is still needed. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. A tick that changed something for the operator ends by catching them up per the `$ketchup` skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the `$ketchup` skill, covering each PR's state and verdict, what merged, countersigns and why, and open operator gates, with links to each PR and the trails.
