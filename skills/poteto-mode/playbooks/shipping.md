### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This is the half after `playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is safe to merge and lands it from the bottom, one PR at a time.

1. **Resolve the forge, then verify each PR independently before it lands.** Resolve GitLab or GitHub once through `../references/forge.md`. One isolated agent VM or remote task per PR runs the change the way a user would with the matching control skill (such as `control-ui` or `control-cli`), parent against head. Each returns one check verdict from [`../references/verdicts.md`](../references/verdicts.md) and posts it on its own PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict. Only `PASS` and `PASS+NOTES` pass. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Record the base SHA, head SHA, and stable `git patch-id` of the base-to-head diff, and compare the recorded patch ID with the current one before trusting an older verdict. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files, so a reader can check the call. If only noise differs, that lane's result stands. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. When only the SHAs changed, keep the code verdict and rerun CI and mergeability at the current head.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR through the selected forge's guarded squash command from `../references/forge.md`. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result, because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm auto-merge only when the user authorized merge when ready, and only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk through the selected forge, move its patch onto the merge result, and push with `--force-with-lease` after a `git ls-remote` check. The verdict covers the patch, not its commits, so step 3's patch-ID rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Use the selected forge's wait command under an authorized thread heartbeat. After each wake, re-read the current bottom PR until it reports merged or blocked. GitHub's `autoMergeRequest` describes one GitHub PR. It does not prove that a descendant is queued or that a patch verdict is current. GitLab auto-merge has the same one-MR scope. If the selected forge cannot confirm the current bottom PR's state, report it as unknown. A base that moves to trunk when its parent merges is expected, not damage to repair. After each merge, fetch trunk, confirm that it contains the merge, remove that PR from the frozen bottom-to-top list, and inspect the new bottom PR's base, head, checks, and patch ID. Independent work stays outside the chain. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the selected forge, the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
